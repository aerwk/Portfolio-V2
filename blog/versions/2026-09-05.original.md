# September 5, 2026

Yesterday's audit found four things that looked fine and weren't: a quota, a scheduler, a retention tool, and a set of backups, each one passing its own health check while doing nothing. Today found out why they weren't four things. They were one thing. A storage pool on the NAS had gone read-only on the 28th, and a home automation VM, a container, a backup datastore and a backup target all had disks living on that pool. Four services, one filesystem. The day was spent proving that, and then getting off it.

The working theory going in was metadata corruption, which pointed at a rescue mount as the fix. A scrub said otherwise.

## The scrub that changed the plan

The pool had logged `parent transid verify failed` and 150 corruption errors before it dropped itself read-only. That reads like structural damage, the kind a rescue mount is built for. The scrub proved the metadata was clean and found something else: 8 uncorrectable data checksum errors, in two archived video files that had nothing to do with the filesystem's own bookkeeping.

That result changed the plan, not just the diagnosis. A rescue mount was no longer needed, and `--repair` was explicitly rejected, because the array has no redundancy. There is nothing to repair against. Running it anyway would have meant asking btrfs to guess at the correct bytes with no second copy to check the guess, which is a way to make an array worse, not better.

Both drives passed SMART, which mattered as much as the scrub result. A dying disk and corrupted filesystem metadata call for different responses, and the SMART pass ruled out the first one before any decision got made.

The part worth sitting with is the reboot. A firmware reboot brought the pool back writable, and on its own that looks like the problem solved itself. It had done exactly the same thing on the 28th: read-write again after a reboot, then it aborted again three days later. A reboot that clears a symptom is not a fix, and the corrupt blocks were still sitting on disk regardless of whether the pool would currently accept a write.

## What cluster HA doesn't let you do

Getting guests off the pool meant stopping them first, and the cluster's HA management would not allow a plain stop. `qm stop` or `pct stop` on a guest under HA gets reverted: the manager notices the guest is down and restarts it. Every stop in this recovery had to go through `ha-manager set` with `--state disabled` first, or the step would look complete and then quietly undo itself a few seconds later.

The home automation VM and the model proxy VM both got restored from backup to node-local storage rather than repaired in place. Neither restore was trusted on completion alone. The VM got HTTP 200 on the service, a read-write check on its data mount, the bridge listening on its port, and both monitors reporting up within 45 seconds, before the temporary ID was renumbered back to the original. The proxy VM turned up an unrelated fact in the process: its running memory was 12,288 MB against a config that displayed 8,192, a memory increase that had been set but never applied. The restore kept the true, larger value rather than the stale config number.

The container was different, because its problem was a journal abort rather than a dead disk. The reboot window was used deliberately: HA disabled, `pct fsck` run (it recovered cleanly, exit 0), the volume moved to local storage with the original kept as a forensic copy, then started. All four of its workflows came back and were confirmed registering in the logs, not just reported active.

## Trusting the backups before trusting anything else

Every archive pulled from that datastore got run through `zstd -t` before it was used for anything. A backup taken through a filesystem that is already degraded can complete successfully and still contain corrupted data, because the backup job proves the copy moved, not that the source was intact when it was read. That distinction did the actual work here: it is why the restores that followed could be trusted rather than assumed.

The mistake worth keeping came earlier, copying data off the failing pool by hand. The first attempt ran through `sudo -i`, which dropped the destination variable partway through the command. The copy went to the NAS root overlay instead of the target pool, filled it to 100%, and hung. Re-run correctly the second time, but a shell that silently drops your environment mid-command is a good way to send hundreds of gigabytes somewhere you didn't mean to send them.

One alarm got investigated and deliberately left alone. Roughly 150 scheduled credential-session runs over three days produced about 4 intermittent failures, every one self-healing on the next run. The likely cause is a check-then-use race, not a scheduling bug, and no fix went in: units that fail closed and retry are already safe, and chasing a self-healing intermittent manufactures more alarms than it prevents.

Everything that had a disk on that pool is now off it, on node-local storage instead, which trades the ability to move those guests between nodes for not depending on that box's health. The pool itself is back writable. Whether it stays that way is not known. It did the same thing a week ago and came back down three days later, so the honest plan is to watch it for the next day and not call it fixed until it has stayed up longer than that.
