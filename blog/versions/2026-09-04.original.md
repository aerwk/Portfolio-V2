# September 4, 2026

Seven days away, then a full read-only pass through the lab to see what had actually happened while nobody was watching. The audit found four separate things that had every green light lit the whole time and had not been doing their job for any of it. The shape repeats across all four: a liveness check was standing in for a correctness check. The process was alive, the API answered, the container said Up, the job fired on schedule, and none of that touched whether the actual work was happening.

Nothing got fixed today. That was a decision, not an oversight: no restart, no filesystem check, no config edit, no deletion, even where the fix looked obvious and cheap. The evidence needed to stay exactly as broken as it was found, so every failure could be read off the running systems rather than reconstructed from memory afterward. The fixes are a separate day.

## The number that was real and wrong

The seedbox filled up and took the library server down with it, and every instrument disagreed with the one number that mattered. `df` reported 4.6 TB available, 82% full. Uptime Kuma agreed. Prometheus and Grafana agreed. Both applications' own free-space APIs agreed. `quota -s` told a different story: the account's quota sat at 99.9% full, about 20 GiB of headroom left.

The provider enforces a per-user quota that `statfs` cannot see. `df` was reading the shared underlying volume, a real number, accurately reported, describing somebody else's disk. Every threshold in the lab had been sized against a figure that was never going to move, because it was never the figure that mattered.

The download client's own log had the first honest line: `Disk quota exceeded` at 06:08, with six zero-byte files scattered across the preceding days marking the failed writes. The library server crashed seven minutes later. Recovery took roughly 46.5 hours, and it recovered on its own, sometime before the audit even started looking. Worked back from a known baseline, the burn rate is about 61 GB/day over the prior 13 days, which makes the fill date arithmetic, not a surprise. Nothing was watching the number that would have predicted it.

## The retention job that had deleted nothing, ever

The retention tool's health endpoint returned 200 on every check for 13 days straight. Container healthy, RestartCount 0, scheduled runs firing on time in its own logs. A live query against its rules API told a different story: `handledMediaAmount: 0` and `handledMediaSizeBytes: 0` on all six collections. Not below target. Zero bytes moved since the day it was deployed.

Two separate causes were stacked on top of each other. Five of the six collections were structurally disarmed by a ten-year grace period, a safety catch set once and never released, holding back roughly 1.01 TB that could not have been deleted even if everything else worked. The sixth collection was armed and failed anyway, on every run, because the stored API key had gone stale: the stored key returns 401, the live key sitting in the app's own config returns 200. Same failure, four days running.

None of it alerted, because the tool notifies on a successful action and has no signal for a failed one. Four days of daily failures produced zero notifications. Why the two keys diverged is unresolved. The config is bind-mounted and survives a container recreate, so a restart doesn't explain it.

## The scheduler that was Up and had run nothing

The automation platform reported 4 of 4 workflows active, container Up 7 days, and its own log from the week-earlier restart showed "Activated workflow" for all four. `docker logs --since` across the whole week returns zero lines. No ticks, no errors, nothing. Executions between 2026-08-28 and today: zero. The practical result is that no OS, container, or hypervisor update ran anywhere in the lab for a week, and the only way to see that was to query the executions table directly, because the API's own health answer said everything was fine.

Two more things were down without a settled cause. A backup job fired at 01:00 on all three nodes every night and failed every one of them: filesystem errors reading ownership files on the datastore, garbage collection failing its own safety check even on a chunk that should have read clean. A parallel job to different storage caught most of it, except for one guest that failed all seven nights on its own I/O error. And a home automation VM read `running` with a guest agent answering ping the whole time, while the service inside it had refused connections since 2026-08-31 00:06Z, confirmed independently by both monitoring instances. Neither root cause is established.

One candidate for the scheduler: a five-minute read-only remount of its container's filesystem on 2026-08-28, sitting between its last successful run and the next one it never made. That service keeps its state in SQLite on that filesystem, and a database going read-only under a live process is a plausible way to kill a scheduler while leaving its HTTP endpoint answering. It stays a hypothesis. Nothing in the log proves it.

## What checked out

Not everything was rot. The planned reboot came back with zero failed units and every mount writable. An application restart logged RestartCount 0 and exit 0, genuinely benign. Cluster quorum held 3 of 3 with no fencing. Tunnels dropped briefly and reconnected on their own. One alert about an unreachable service turned out to be a stale monitor still pointed at that service's address from before it moved, not an outage at all. An audit that finds nothing but bad news is usually one that went looking for it, and this one didn't.

What it did find is a pattern worth carrying into tomorrow: a status that means "alive" was doing the job of a status that means "correct," in every one of these systems, and the gap between the two only showed up once someone went and read the underlying data by hand instead of trusting the check built to report it.
